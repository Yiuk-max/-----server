# 社区后端改造方案（v4：社区独立表 + 独立成员表）

> 状态：设计稿（DB 迁移脚本已就绪：`sql/community.sql`）
> 范围：**只讨论后端**。前端形态仅作为需求上下文，不在本文实现范围。

---

## 1. 设计原则

- **社区是独立表 `community`**，与普通群聊的 `Group` 彻底分开，不互相硬塞语义。
- `community` 表同时装两类行：**核心频道**（社区本身）+ **普通频道**。
- **社区成员独立表 `community_member`**，挂在核心频道上，一份共享给所有普通频道。
- 普通群聊 `Group` / `Groupmember` **完全不动**。
- 频道消息复用 `message` 表，用 `type='channel'` 与普通群聊（`type='group'`）区分。

```
community（独立社区表）
├── 核心频道 (is_core=1, 隐藏)
│     name=社区名, description=社区简介, avatar=社区头像, owner_UID=社区拥有者
│     └── community_member（社区成员，一份，所有普通频道共享）
└── 普通频道 (is_core=0)
      name=频道名, category=分区, description/avatar/owner_UID=NULL
      core_channel_id → 核心频道id

Group（原表，普通群聊，完全不动）
  └── Groupmember（原表，普通群成员）
```

## 2. 数据模型

### 2.1 社区表 `community`（新增，独立表）

| 字段 | 类型 | 作用 |
|---|---|---|
| `id` | BIGINT UNSIGNED AUTO_INCREMENT PK | 社区/频道 ID |
| `name` | VARCHAR(64) NOT NULL | 社区名(core) / 频道名(channel) |
| `core_channel_id` | BIGINT UNSIGNED NULL | 普通频道→核心频道id；核心频道为 NULL |
| `is_core` | TINYINT(1) NOT NULL DEFAULT 0 | 1=核心频道(社区，隐藏不展示) |
| `description` | VARCHAR(255) NULL | 社区简介（仅核心频道） |
| `avatar` | VARCHAR(128) NULL | 社区头像 file_id（仅核心频道，预留） |
| `owner_UID` | BIGINT UNSIGNED NULL | 社区拥有者（仅核心频道） |
| `category` | VARCHAR(64) NULL | 频道分区（普通频道） |
| `create_time` | DATETIME DEFAULT CURRENT_TIMESTAMP | 创建时间 |

自引用外键：`core_channel_id → community(id) ON DELETE CASCADE`（删社区=删核心频道，级联删普通频道）。

### 2.2 社区成员表 `community_member`（新增，独立表）

| 字段 | 类型 | 作用 |
|---|---|---|
| `community_id` | BIGINT UNSIGNED | 所属社区（=核心频道id） |
| `user_UID` | BIGINT UNSIGNED | 成员 UID |
| `nickname` | VARCHAR(64) NULL | 社区内昵称（NULL=全局昵称） |
| `role` | ENUM('owner','admin','member') DEFAULT 'member' | 社区角色 |
| `join_time` | DATETIME DEFAULT CURRENT_TIMESTAMP | 加入时间 |

- 社区成员 = `community_member WHERE community_id = 核心频道id`（一份，所有普通频道共享）。
- 普通频道**不维护成员**，成员继承其 `core_channel_id` 指向的社区。

### 2.3 普通群聊（不动）

`Group` / `Groupmember` 原样保留，普通群聊功能零回归。

### 2.4 用户头像

`Account.avatar_file_id`（预留，二期文件传输落地）。

### 2.5 消息类型（英文枚举）

`message.type` 由 TINYINT 改为英文枚举：

| type | 语义 | receiver_UID |
|---|---|---|
| `private` | 私聊 | 对方 UID |
| `group` | 普通群聊 | Group.group_UID |
| `channel` | 社区频道 | community.id（频道 id） |

## 3. 关键 SQL（repo 层实现）

### 3.1 频道成员 = 社区成员

```sql
-- 某频道（community.id=?) 的成员 = 其核心频道下的社区成员
SELECT cm.user_UID, cm.nickname, cm.role
FROM community ch
JOIN community_member cm ON cm.community_id = ch.core_channel_id
WHERE ch.id = ? AND ch.is_core = 0;
```

### 3.2 我的社区 / 我的频道 / 社区频道列表

```sql
-- 我加入的社区（核心频道）
SELECT c.id
FROM community_member cm
JOIN community c ON c.id = cm.community_id
WHERE cm.user_UID = ? AND c.is_core = 1;

-- 我在社区里可见的所有普通频道
SELECT ch.id
FROM community_member cm
JOIN community ch ON ch.core_channel_id = cm.community_id
WHERE cm.user_UID = ? AND ch.is_core = 0;

-- 某社区（核心频道id=?）下的普通频道列表
SELECT id, name, category
FROM community
WHERE core_channel_id = ? AND is_core = 0
ORDER BY category, id;
```

### 3.3 离线消息：加入频道（type='channel'）

`message_repo::get_offline_messages` 在现有私聊/群聊基础上追加：

```sql
-- 社区频道离线消息
m.type = 'channel' AND m.receiver_UID IN (
    SELECT ch.id
    FROM community_member cm
    JOIN community ch ON ch.core_channel_id = cm.community_id
    WHERE cm.user_UID = ? AND ch.is_core = 0
)
```

### 3.4 频道历史：按 type='channel' 查

`get_history_page` 对频道（is_channel=true）走：

```sql
WHERE m.type = 'channel' AND m.receiver_UID = ? AND m.id < ?
ORDER BY m.id DESC LIMIT ?
```

### 3.5 删除社区时的消息清理

```sql
-- 先删该社区所有普通频道的消息，再删核心频道（频道由外键级联删）
DELETE FROM message WHERE type = 'channel' AND receiver_UID IN (
    SELECT id FROM community WHERE core_channel_id = ? AND is_core = 0
);
DELETE FROM community WHERE id = ?;
```

## 4. 协议改造（`src/proto/message.proto`）

### 4.1 新增结构

```proto
message CommunityInfo {
  int32  community_id   = 1;  // 核心频道 id
  string name           = 2;
  string description    = 3;
  string avatar         = 4;  // file_id，预留
  string category       = 5;  // 预留：社区所属分区

message ChannelInfo {
  int32  channel_id   = 1;  // 普通频道 id
  int32  community_id = 2;  // 核心频道 id
  string name         = 3;
  string category     = 4;  // 频道分区

message MemberInfo {
  int32  user_uid = 1;
  string nickname = 2;  // 社区昵称（NULL 时前端用全局昵称）
  string role     = 3;
}
```

### 4.2 Envelope 追加字段（编号从 33 起）

```proto
int32  community_id   = 33;  // 社区（核心频道）id
```

## 5. 后端分层改造

### 5.1 新增 `I_community_repo` + `community_repo`

新增 `src/db/repo_interface/community_repository.h` 与 `src/db/repo/community_repo.h/.cpp`（SQL 只写在 community_repo.cpp）。

```cpp
class I_community_repo {
public:
    virtual ~I_community_repo() = default;

    // ---- 社区（核心频道） ----
    virtual int  create_community(int owner_uid, const std::string& name,
                                  const std::string& description) = 0; // 返回核心频道id
    virtual bool delete_community(int community_id, int requester_uid) = 0;
    virtual bool modify_community(int community_id, int requester_uid,
                                  const std::string& name,
                                  const std::string& description,
                                  const std::string& avatar) = 0;

    // ---- 查询 ----
    virtual bool is_community_member(int community_id, int user_uid) = 0;
    virtual std::vector<int> get_user_communities(int user_uid) = 0;
    virtual std::vector<int> get_user_channels(int user_uid) = 0;
    virtual bool get_community_channels(int community_id,
                                        std::vector<ChannelInfo>& out) = 0;
    virtual bool get_community_members(int community_id,
                                       std::vector<MemberInfo>& out) = 0;

    // ---- 频道 ----
    virtual int  create_channel(int community_id, int requester_uid,
                                const std::string& name,
                                const std::string& category) = 0; // 返回频道id
    virtual bool delete_channel(int community_id, int channel_id, int requester_uid) = 0;
    virtual bool modify_channel(int community_id, int channel_id, int requester_uid,
                                const std::string& name,
                                const std::string& category) = 0;

    // ---- 成员 ----
    virtual bool add_member(int community_id, int requester_uid, int target_uid) = 0;
    virtual bool remove_member(int community_id, int requester_uid, int target_uid) = 0;
    virtual bool leave(int community_id, int user_uid) = 0;
    virtual bool send_join_request(int community_id, int requester_uid,
                                   const std::string& message) = 0;
    virtual bool handle_join_request(int community_id, int requester_uid,
                                     int target_uid, bool accept) = 0;
    virtual bool modify_member_role(int community_id, int requester_uid,
                                    int target_uid, bool promote) = 0;
    virtual bool show_requests(int community_id, int requester_uid,
                               std::vector<std::tuple<int, std::string>>& out) = 0;

    // ---- 频道成员（供发言/删除广播） ----
    virtual std::vector<int> get_channel_members(int channel_id) = 0;
};
```

实现要点：

- `create_community`：`INSERT community(name, is_core=1, description, owner_UID)` → `INSERT community_member(community_id, owner, role='owner')`。
- `create_channel`：校验 requester 是社区成员 → `INSERT community(name, is_core=0, core_channel_id=社区id, category)`。
- `delete_community`：校验 owner → 删频道消息(type='channel') → `DELETE community WHERE id=?`（频道+成员级联删）。
- 入社区申请复用 `relation_apply`，新增 `apply_type=3`（group_UID 列存 community_id）。

### 5.7 消息删除广播

`chat_handler.cpp` 的 `delete_message` 里按 `message.type` 路由：
- `group` → 现有群聊广播（`get_group_members`）。

### 5.8 Redis 缓存接入（Cache-Aside，与现有 Redis 方案一致）

社区功能的高频读与现有群聊一样，走「repo 内部先查 RedisCache，未命中回 MySQL 后回填；
写路径主动失效」模式，`redis.enabled=false` 时自动降级回 MySQL。复用现有 `RedisPool` /
`RedisCache`，只新增 key 与缓存方法。

#### 5.8.1 缓存点

| 缓存点 | key | 类型 | 内容 | 优先级 |
|---|---|---|---|---|
| C7 社区成员列表 | `chat:c:members:{community_id}` | SET | 社区成员 uid | ⭐ 最高（频道发言广播每消息一次） |
| C8 频道信息 | `chat:c:channel:{channel_id}` | HASH | community_id/name/category/is_core | ⭐ 高（频道校验 + 解析所属社区） |
| C9 社区频道列表 | `chat:c:channels:{community_id}` | ZSET | channel_id（score=category+id） | 中（进社区加载频道列表） |
| C10 用户社区/频道列表 | `chat:c:ucommunities:{uid}` / `chat:c:uchannels:{uid}` | SET | 社区/频道 id | 中（登录加载） |
| C11 社区信息 | `chat:c:info:{community_id}` | HASH | name/description/avatar/owner_UID | 低（低频读） |

#### 5.8.2 读写流程

- **C7 社区成员**：
  - 读：`community_repo::get_channel_members(channel_id)` 先解析出 community_id（命中 C8），
    再 `SMEMBERS chat:c:members:{community_id}`；未命中查 `community_member` 回填 `SADD`。
  - `is_community_member` 直接 `SISMEMBER` 该 SET。
- **C8 频道信息**：
  - 读：`community_repo::load_channel(channel_id)` 先 `HGETALL chat:c:channel:{channel_id}`，
    未命中查 `community` 表回填 `HSET` + 兜底 TTL。
- **C9 社区频道列表**：
  - 读：`get_community_channels` 先 `ZRANGE`，未命中查 `community` 表回填 `ZADD`。
- **C10 用户社区/频道列表**：
  - 读：登录 `social_module` 加载时先 `SMEMBERS`，未命中查库回填。
- **C11 社区信息**：
  - 读：`get_community` 先 `HGETALL`，未命中查 `community`(is_core=1) 回填。

#### 5.8.3 失效矩阵（写路径全部主动失效）

| 写操作 | 失效 key |
|---|---|
| `create_community` | 无（新建，`SADD` owner 到 C7 即可） |
| `delete_community` | DEL C7 / C8(该社区所有频道) / C9 / C11 |
| `modify_community` | DEL C11 |
| `create_channel` | DEL C9（新频道下次读回源） |
| `delete_channel` | DEL C8(channel) / C9 |
| `modify_channel` | DEL C8(channel) / C9 |
| `add_member` / `handle_join_request(accept)` | DEL C7 / C10(目标用户) |
| `remove_member` / `leave` | DEL C7 / C10(目标用户) |
| `modify_member_role` | DEL C7（若后续 C7 改存 role 时） |

> 说明：频道成员与社区成员是同一份数据，所以广播只需要 C7（按 community_id），
> 不需要为每个频道各存一份成员列表；这是本设计相比普通群聊更省缓存的一点。
> 兜底 TTL：C8/C9/C10/C11 建议 24h；C7 无 TTL + 主动失效（与现有 C1 群成员一致）。

#### 5.8.4 降级

与现有 Redis 方案一致：Redis 异常/未启用 → 返回未命中 → 回退 MySQL，业务语义不变。

## 6. 关键流程

### 6.1 建社区

```
create_community(name, description)
  → INSERT community(name, is_core=1, description, owner_UID) → community_id
  → INSERT community_member(community_id, owner, role='owner')
  → 回执 system：Community created. ID: <community_id>
```

### 6.2 建频道

```
create_channel(community_id, name, category)
  → 校验 requester ∈ community_member
  → INSERT community(name, is_core=0, core_channel_id=community_id, category)
  → 不写成员
```

### 6.3 频道发言

```
channel_chat(channel_id, msg)
  → 校验频道存在 + 发送者 ∈ 所属社区
  → message_repo.store_message(type='channel', receiver_UID=channel_id)
  → community_repo.get_channel_members(channel_id) → 社区成员
  → NoticeService 广播 Channel_Chat
```

### 6.4 频道历史 / 离线

```
history_request(peer_id=channel_id, is_channel=true)
  → message_repo.get_history_page(..., type='channel', peer_uid=channel_id)

离线消息登录补发：get_offline_messages 覆盖 type='channel' 频道消息。
```

### 6.5 删社区

```
delete_community(community_id)
  → 校验 owner
  → 删频道消息(type='channel', receiver_UID IN 该社区频道)
  → DELETE community WHERE id=community_id（频道+成员级联删）
```

## 8. 风险与注意事项

1. **ID 命名空间**：`community.id` 与 `Group.group_UID` 是两套独立自增，可能撞号；靠 `message.type`（'group'/'channel'）和协议 type（group_chat/channel_chat）区分，无歧义。
2. **孤儿消息**：删社区/频道前必须手动删 `message.type='channel'` 消息（无 FK 级联）。
3. **消息路由**：所有"群聊"相关逻辑（历史/离线/删除广播）都要补 type='channel' 分支，不能只改发送。
4. **`has_group` 与 `has_channel` 分开**：历史查询靠 `is_channel` 明确区分，避免撞号歧义。
5. **老数据兼容**：新表独立；message.type 迁移脚本会把老数据 1/2 映射为 'private'/'group'，老数据不受影响。
6. **文件字段**：`avatar` 一期只存不读，二期文件传输落地后再消费。
