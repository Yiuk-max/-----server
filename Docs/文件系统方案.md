# 文件系统方案（统一 File 体系 / 磁盘存储 / 分片传输 / 暂停续传）

> 状态：设计稿（本文件为权威版本，配套脚本见同目录 `../sql/`）。
> 目标：把"文件"做成与消息解耦的基础设施，头像、Emoji、聊天图片、聊天附件、普通文件
> 全部走同一套 `File` 元数据 + 磁盘存储 + 分片传输体系。

---

## 策略
达到文存储10GB上限制后，去找最老的文件，删除文件和数据库记录
申请上传要审核大小

## 1. 核心原则

1. **数据库只描述文件，不存文件本体**：`file` 表回答"谁传的、叫什么、多大、什么类型、
   存在哪、什么时候传、哈希是什么"，二进制全部放磁盘。
2. **文件路径由 Storage 层生成，数据库不依赖目录分类**：DB 只保存 `storage_key` 和 `type`，
   真正的 `/home/ubuntu/chat_server_files/files/<type>/<aa>/<key>` 由 `FileStorage` 生成。
3. **不直接用原始文件名当磁盘文件名**：同名、中文、特殊字符、路径穿越、恶意名、覆盖等问题
   一律由服务器生成的 `storage_key`（UUID / 随机）规避；原始名只存 `file.original_name`，
   下载时通过 `Content-Disposition` 还给客户端。
4. **大文件流式读写，不整块进内存**：分片上传 `open→write(chunk)*N→close`，分片下载
   `open→read(chunk)*N→close`；任何 500 MB 文件都不会同时进入内存。
5. **文件传输与消息解耦**：`Message`、`User`、`CustomEmoji` 只保存 `file_id` 引用，
   真正的传输/下载是独立接口。

```
┌─────────────────────────── client_session ───────────────────────────┐
│  FileHandler（解析 Envelope → 调 FileService）                        │
│        │                                                             │
│        ▼                                                             │
│  FileService（上传/下载/分配/暂停/续传/进度，与网络层无关）             │
│        │                    │                                        │
│        ▼                    ▼                                        │
│  FileStorage（磁盘流式读写） I_file_repo（MySQL 元数据/传输会话）      │
└──────────────────────────────────────────────────────────────────────┘
        │ 通过 IClientTransport::send_packet(env, file_data) 发块
        ▼
┌──────────────────────────────────────────────────────────────────────┐
│  binary: connection::send_packet(env, file_data)                     │
│  ws    : WsSession::send_packet(env, file_data)                      │
```

- `FileStorage`：磁盘工具类，负责路径生成、流式写/读、临时文件、原子改名、sha256。
- `I_file_repo / file_repo`：沿用 `repo_interface` / `repo` 分层，由 `RepositoryHub` 装配。
- `FileService`：业务编排层，只依赖 `FileStorage` + `I_file_repo` + `IClientTransport`，
  对 binary / websocket 无感知。

## 3. 存储目录

### 3.1 根目录（可配置）

```json
"file_storage": {
    "root": "/home/ubuntu/chat_server_files",
    "chunk_size": 4194304,
    "max_chunk_size": 16777216,
    "max_file_size": 536870912,
    "max_storage_size": 10737418240,
    "max_avatar_size": 10485760,
    "transfer_timeout_seconds": 1800
}
```

- `root`：存储根目录，直接使用 `/home/ubuntu/chat_server_files`。
- `chunk_size`：分片大小，默认 4 MiB（见 §5）。
- `transfer_timeout_seconds`：watchdog 超时，超过该秒数无活动则清理（默认 1800s）。

### 3.2 目录布局

```
<root>/
├── files/
│   ├── avatar/       # 用户头像
│   ├── emoji/        # 自定义 Emoji
│   ├── image/        # 聊天图片
│   ├── attachment/   # 聊天附件
│   └── file/         # 普通文件（兜底类型）
│       └── a8/a83f9c...            # 每类下按 storage_key 前 2 字符分片
└── tmp/
    └── <transfer_id>.part          # 上传中的临时文件
```

- 目录分类只存在于 **Storage 层**，DB 的 `file` 表只存 `storage_key` + `type`，不感知目录结构。
- `storage_key` = 服务器生成的随机唯一键（UUID v4 去横线或 32 位随机 hex）。
  最终路径：`files/<type>/<storage_key前2字符>/<storage_key>`。
- 上传先写 `tmp/<transfer_id>.part`，全部块到达且 hash 校验通过后原子 `rename()` 到正式路径。
- watchdog 负责清理 `tmp/` 下超时残留与"孤儿"正式文件。

## 4. 数据库设计

### 4.1 新表 `file` —— 只描述文件

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `BIGINT UNSIGNED AUTO_INCREMENT` | 文件唯一 ID（对外 string 化） |
  | `uploader_uid` | `BIGINT UNSIGNED NOT NULL` | 上传者 |
| `storage_key` | `VARCHAR(191) NOT NULL` | 磁盘文件唯一键（服务器生成，非原始名） |
| `type` | `ENUM('avatar','emoji','image','attachment','file') NOT NULL DEFAULT 'file'` | 文件类别、文件用途分类 |
| `original_name` | `VARCHAR(255) NOT NULL` | 原始文件名（仅展示/下载回显） |
| `mime_type` | `VARCHAR(128) NULL` | MIME 类型 ，文件真正的格式|
| `size` | `BIGINT UNSIGNED NOT NULL DEFAULT 0` | 字节数 |
| `hash` | `CHAR(64) NOT NULL` | sha256（完整性校验） |
| `created_at` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP` | 上传时间 |

索引：`PRIMARY KEY(id)`、`UNIQUE KEY uk_storage_key(storage_key)`、`KEY idx_uploader(uploader_uid)`。
外键：`uploader_uid -> Account.UID ON DELETE CASCADE`。

> 关键：`storage_key` 与 `hash` 分开。`storage_key` 负责"存哪"（随机唯一，避免内容寻址带来的
> 多归属/覆盖问题）；`hash` 负责"校验是否完整"（sha256，可另做去重优化）。

### 4.2 新表 `file_transfer` —— 传输会话（分片/断点/暂停续传）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `BIGINT UNSIGNED AUTO_INCREMENT` | 传输会话 ID |
| `file_id` | `BIGINT UNSIGNED NULL` | 目标文件；上传完成前为 NULL，完成后回填 |
| `uploader_uid` | `BIGINT UNSIGNED NOT NULL` | 上传方/发送方 |
| `receiver_uid` | `BIGINT UNSIGNED NULL` | 接收方（头像/emoji 等无接收方可空） |
| `direction` | `ENUM('upload','download') NOT NULL` | 上传 / 下载 |
| `status` | `ENUM('uploading','downloading','paused','completed','cancelled','failed') NOT NULL` | 会话状态机 |
| `total_size` | `BIGINT UNSIGNED NOT NULL DEFAULT 0` | 总字节数 |
| `transferred_size` | `BIGINT UNSIGNED NOT NULL DEFAULT 0` | 已完成字节数（进度冗余） |
| `chunk_size` | `INT UNSIGNED NOT NULL DEFAULT 4194304` | 分片大小（默认 4 MiB） |
| `chunk_count` | `INT UNSIGNED NOT NULL DEFAULT 0` | 总分片数 |
| `next_chunk_index` | `INT UNSIGNED NOT NULL DEFAULT 0` | 顺序传输的断点块号 |
| `received_bitmap` | `VARBINARY(4096) NULL` | 乱序重组位图（1 bit / chunk，支持精确续传） |
| `tmp_path` | `VARCHAR(512) NULL` | 上传中临时文件相对路径 |
| `storage_key` | `VARCHAR(191) NULL` | 上传目标 storage_key（断线重连续传用） |
| `file_type` | `VARCHAR(16) NULL` | 文件类别（断线重连续传用） |
| `original_name` | `VARCHAR(255) NULL` | 原始文件名（断线重连续传用） |
| `mime_type` | `VARCHAR(128) NULL` | MIME 类型（断线重连续传用） |
| `last_active_at` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` | watchdog 依据 |
| `created_at` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP` | 创建时间 |
| `updated_at` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` | 更新时间 |

索引：`PRIMARY KEY(id)`、`KEY idx_file(file_id)`、`KEY idx_uploader(uploader_uid)`、
`KEY idx_receiver(receiver_uid, status)`、`KEY idx_watchdog(status, last_active_at)`。
外键：`file_id -> file(id) ON DELETE SET NULL`、`uploader_uid -> Account.UID ON DELETE CASCADE`、
`receiver_uid -> Account.UID ON DELETE CASCADE`。

状态机：

```
uploading ──全部块到齐+hash通过──► completed（回填 file_id）
    │
    ├──暂停──► paused ──继续──► uploading
    ├──取消──► cancelled
    └──超时/错误──► failed（watchdog/IO/DB）

downloading 同理，completed 表示接收方已收完全部分片。
```

### 4.3 现有表改造

`sql/alter_existing_tables.sql`：

```sql

-- message 增加"这是一条文件消息"与对应 file_id

    ADD COLUMN is_file TINYINT(1) NOT NULL DEFAULT 0 AFTER content,
```

- **头像**：加载账号时**依旧只返回文字信息**（原有 DB 查询不变），头像通过另一个接口

- **消息**：`is_file=1` 的消息在历史/在线消息里**按文字处理**（只传 `file_id` + 文件名 + 大小等
  元数据），用户点击后才发 `file_download_init` 传输文件本体。

## 5. 分片传输协议

### 5.1 分片大小

- 默认 **4 MiB**，`file_storage.chunk_size` 可配置。
- 约束：`chunk_size <= websocket.max_message_bytes`（当前默认 1 MiB，需调大到 ≥ 4 MiB，
  建议 8 MiB）；binary 帧 `MAX_FRAME_SIZE` 当前 16 MiB，天然满足。

### 5.2 protobuf 增量（`src/proto/message.proto` 只做加法）

```proto
message FileMeta {
  string file_id       = 1;  // string 化的 file.id
  string original_name = 2;
  string mime_type     = 3;
  uint64 size          = 4;
  string hash          = 5;
  string type          = 6;  // avatar/emoji/image/attachment/file
  int32  uploader_uid  = 7;
  string created_at    = 8;
}

message FileTransferInfo {
  string transfer_id      = 1;
  string file_id          = 2;
  int32  uploader_uid     = 3;
  int32  receiver_uid     = 4;
  string direction        = 5;  // upload / download
  string status           = 6;  // uploading/downloading/paused/completed/cancelled/failed
  uint64 total_size       = 7;
  uint64 transferred_size = 8;
  uint32 chunk_size       = 9;
  uint32 chunk_count      = 10;
  uint32 next_chunk_index = 11;
}

// FileChunkMeta 追加（保留原字段号 1~8）：
//   string transfer_id = 9;   // 传输会话 ID（上传/下载分块必带）
//   string hash        = 10;  // 首块可选携带全文件 sha256
```

`Envelope` 追加（从 44 起）：

```proto
FileMeta          file_meta    = 44;
FileTransferInfo  transfer_info = 45;
int32             transfer_id  = 46;
string            file_id      = 47;
repeated FileMeta files        = 48;  // file_list_response
```

### 5.3 消息类型

| type | 方向 | 说明 | 关键字段 |
|------|------|------|----------|
| `file_upload_init` | C→S | 申请上传 | `file_meta{original_name,size,mime_type,type}`、`hash`(可选)、`receiver_uid`(可选) |
| `file_upload_ready` | S→C | 同意上传 | `transfer_info{transfer_id,chunk_size,chunk_count}` |
| `file_chunk` | 双向 | 分片数据 | `meta{transfer_id,chunk_index,offset,chunk_size}` + 帧尾 `file_data` |
| `file_upload_done` | C→S | 客户端发完全部分片 | `transfer_id`、`hash` |
| `file_upload_complete` | S→C | 校验通过、原子落盘 | `file_meta{file_id,...}`、`transfer_info` |
| `file_download_init` | C→S | 申请下载（建会话） | `file_id` |
| `file_download_ready` | S→C | 下载就绪 | `file_meta`、`transfer_info` |
| `file_download_chunk` | C→S | 拉取单个分片（背压/可中断） | `transfer_id`、`chunk_index` |
| `file_upload_resume` | C→S | 断线重续上传 | `transfer_id` |
| `file_transfer_pause` | C→S | 暂停 | `transfer_id` |
| `file_transfer_paused` | S→C | 已暂停（回断点） | `transfer_info` |
| `file_transfer_resume` | C→S | 继续 | `transfer_id` |
| `file_transfer_cancel` | C→S | 取消 | `transfer_id` |
| `file_transfer_status` | C→S | 查进度 | `transfer_id` |
| `file_transfer_progress` | S→C | 进度响应 | `transfer_info` |
| `file_list_request` | C→S | 文件列表 | 分页游标（可选） |
| `file_list_response` | S→C | 文件列表 | `files[]` |
| `file_delete` | C→S | 删除文件 | `file_id` |

> 旧的 `upload_file` / `download_file` 保留但标记 deprecated，新客户端走 `file_*` 系列。

### 5.4 上传时序

```
Client                          Server
  │ file_upload_init              │ 建 file_transfer(uploading, tmp_path)
  │──────────────────────────────►│
  │ file_upload_ready             │
  │◄──────────────────────────────│
  │ file_chunk[0..N] + file_data  │ open(tmp) → write(chunk)*N
  │──────────────────────────────►│
  │ file_upload_done              │
  │──────────────────────────────►│ sha256 校验 → rename 到正式路径
  │ file_upload_complete          │ 建 file 行 → 回填 file_transfer.file_id
  │◄──────────────────────────────│
```

### 5.5 下载时序（拉取式，M4）

```
Client                          Server
  │ file_download_init(file_id)   │ 建 file_transfer(downloading)
  │──────────────────────────────►│
  │ file_download_ready           │
  │◄──────────────────────────────│
  │ file_download_chunk(0)        │ seek(0) → read(chunk) → file_chunk
  │──────────────────────────────►│
  │ file_download_chunk(1)        │ seek(chunk) → file_chunk
  │──────────────────────────────►│
  │ ...（逐块拉取，天然背压）       │
  │ 最后一块完成后                 │ transfer=completed
```

### 5.6 暂停 / 继续 / 取消

- **暂停**：任一方发 `file_transfer_pause`，会话置 `paused`，回 `file_transfer_paused`。
  下载是拉取式，客户端停止发 `file_download_chunk` 即自然暂停。
- **继续**：发 `file_transfer_resume`，会话回到 `uploading/downloading`；
  下载继续按 `next_chunk_index` 拉块，上传继续从断点发块，不重传已完成分片。
- **断线重连**：上传发 `file_upload_resume`（按 `transfer_id` 从 DB 重建 writer）；
  下载重连后查 `file_transfer_status` 得到 `next_chunk_index`，继续拉块。
- **取消**：发 `file_transfer_cancel`。删临时文件，任务置 `cancelled`。
- 断点信息全部落库，**断线重连后可续传**。

## 6. FileStorage 抽象（流式，杜绝整块内存）

```cpp
class FileStorage {
public:
    // 由 type + storage_key 生成正式路径：files/<type>/<aa>/<storage_key>
    static std::string resolve(FileType type, const std::string& storage_key);

    // 上传：流式写
    std::unique_ptr<FileWriter> open_writer(const std::string& tmp_path);
    // FileWriter::write(const char* data, size_t n);
    // FileWriter::commit(FileType type, const std::string& storage_key); // 原子 rename

    // 下载：流式读
    std::unique_ptr<FileReader> open_reader(FileId id);
    // FileReader::read(char* buf, size_t max) -> size_t;   // 返回 0 表示 EOF

    // 小文件便捷接口（头像/emoji 等）
    FileId save(const std::string& data, const FileMetadata& meta);

    bool remove(FileId id);
    static std::string sha256_hex(...);   // 增量 hash
};
```

- `FileWriter/FileReader` 一次只持有一个 chunk 的缓冲，文件大小不影响内存峰值。
- `commit()` 用 `rename()`（同盘原子）从 `tmp/<transfer_id>.part` 移到
  `files/<type>/<aa>/<storage_key>`。

## 7. Watchdog（超时清理）

- 后台定时任务（binary 模式可用主 reactor 定时器，websocket 模式可用 `steady_timer`，
  或统一放到 main 的清理线程），周期建议 60s。
- 扫描 `file_transfer WHERE status IN ('uploading','downloading')
  AND last_active_at < NOW() - INTERVAL ? SECOND`，`?` 取
  `file_storage.transfer_timeout_seconds`。
- 命中会话：置 `failed/cancelled`，删除 `tmp/<transfer_id>.part`，并回收无引用的
  `file` 行与正式文件（孤儿清理）。
- 每收到/发出一个 chunk 就 `touch()` 更新 `last_active_at`。

- **M1 存储 + 数据层**：`FileStorage`、`file`/`file_transfer` 建表、`I_file_repo/file_repo`、配置读取。
- **M2 上传/下载闭环**：`file_upload_init/chunk/done`、`file_download_init/chunk`，跑通单文件。
- **M3 引用接入**：`Account.avatar_id` 头像两段式加载、`message.is_file/file_id` 文件消息按文字传、点击下载。
- **M4 暂停/续传/取消/watchdog**：断点位图、超时清理、断线重连续传。
- **M5 管理**：文件列表/删除、孤儿回收、大文件/并发/重连压测。
