# WebSocket 聊天服务器压力测试方案

> 目标：为 `net_layer=websocket` 的聊天服务器建立一套可复用的压测体系，量化「连接、登录、私聊、群聊、离线消息、心跳、顶号、内存池回收」等关键路径的吞吐、延迟、稳定性与资源占用，并沉淀为回归基线。

---

## 1. 目标与范围

### 1.1 目标

1. 摸清服务器在典型业务负载下的**容量上限**（最大并发连接数、最大消息吞吐 msg/s）。
2. 量化各业务路径的**端到端延迟**（握手、登录、私聊投递、群聊广播、离线补发）。
3. 验证**稳定性**：长稳、连接抖动（churn）、内存池回收、fd 泄漏。
4. 验证**异常处理**：超大帧、坏帧、发送队列溢出、空闲超时、顶号。
5. 形成**可重复执行的回归基线**，以后每次架构改动（如刚加的内存池）都能对比。

### 1.2 范围

- 被测对象：`src/net_core_ws/` 的 WebSocket 网络层 + 共享业务层（`client_session` 等）。
- 压测协议：WebSocket binary 帧 `| 4B payload_len(网络序) | protobuf Envelope |`。
- 路径：`ws://<host>:8080/ws`（服务端 IPv6 双栈，`configure.json` 中 `net_layer=websocket`）。
- 本次暂不覆盖：文件传输（WS 模式未实现）、TCP binary 模式。

### 1.3 非目标

- 不做浏览器前端 UI 压测（只测后端 WS 协议层）。
- 不做 MySQL 单独的基准（但会把 DB 作为瓶颈点观测）。

---

## 2. 现状与关键瓶颈假设

压测前先认清被测系统的结构，这些是**重点观测点**，也是压测要「逼出来」的瓶颈：

| 模块 | 现状 | 压测关注点 |
|---|---|---|
| Asio io_context | `ws_io_threads`，默认 4 | 连接建立/收发的网络线程吞吐 |
| 业务线程池 | `ws_server.cpp` 中硬编码 `ThreadPool(8)` | **CPU 密集点**：protobuf 解析 + 业务逻辑 + DB 调用都在这 8 个线程串行执行 |
| MySQL 连接池 | `db_conn_count`，默认 4 | 每次聊天都 `store_message` 落库，DB 很可能先成为瓶颈 |
| 单连接读背压 | 一条消息处理完才发起下一次读 | 单连接串行，但业务线程池饱和时表现为「全服延迟上升」 |
| 发送队列 | 每连接 `max_pending_bytes` 8 MiB，超限 `teardown` | 慢消费者场景下验证背压与主动断开 |
| session_manager | `shared_mutex` + `unordered_map<UID, session>` | 高并发登录/查找的锁竞争 |
| **内存池（本次新增）** | `ClassMemoryPool<client_session, 256, 32>`，最多 8192 个会话对象 | churn 场景下验证「复用/回收/无泄漏」，RSS 是否回落 |
| 系统资源 | fd 上限、ephemeral 端口、somaxconn | 客户端与服务端都要调优，否则「测的是本机限制，不是服务器」 |

> 结论：压测一定要**同时采集服务端 CPU / RSS / fd / 连接数 / MySQL 连接数**，否则只能看到「慢了/断了」，定位不了原因。

## 3. 为什么现成工具不合适（结论：自研）

| 工具 | 适合 | 对本项目的不适点 |
|---|---|---|
| k6（xk6-websocket / experimental websockets） | HTTP/WS 长连吞吐 | 需要自定义扩展才能拼 `4B len + protobuf` 二进制帧；**无法校验业务语义**（登录成功、好友通知、群聊广播、离线补发） |
| Locust（locust-plugins WS） | Python 写场景，业务语义好写 | GIL 限制单进程并发，大规模要多 worker；二进制 protobuf 要自己拼 |
| JMeter / Gatling | 协议录制回放 | WebSocket 支持弱，二进制帧 + 复杂会话流程维护成本高 |
| Artillery | WS 简单压测 | 偏字符串消息，二进制 protobuf 与多步业务流不友好 |
| wrk / ab | HTTP | 不支持 WebSocket |
| websocat / wscat | 手工调试 | 无并发/统计能力 |

**核心矛盾**：本服务的「一条消息」是「WebSocket binary 帧 + 4 字节长度头 + protobuf 业务体」，且压测必须跑完整业务流（注册→登录→加好友→私聊/群聊→离线→顶号），还要**成对校验投递延迟**。现成工具要么不支持二进制业务体，要么做不了端到端业务断言。

因此**自研一个轻量压测客户端**（先单机，跑不动再扩展 controller+agent），是性价比最高的方案。

## 4. 压测工具架构设计（建议）

### 4.1 技术选型

| 语言 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **Go（推荐）** | goroutine 天生高并发、内存低、`gorilla/websocket` 或 `nhooyr.io/websocket` 成熟、protobuf 代码生成简单 | 团队需会 Go | ✅ 首选 |
| Node.js（`ws` + `protobufjs`） | 前端已用 protobufjs，可复用 .proto 生成；开发快 | 单进程单线程，高并发要 cluster | 备选（团队熟 JS 时） |
| C++（boost::beast） | 与服务器同栈，可复用 `message.pb.h` | 开发慢、迭代成本高 | 只在需要超大规模时考虑 |
| Python（asyncio + websockets） | 与冒烟脚本同生态，上手快 | 单进程吞吐低 | 仅做功能/低并发冒烟，不做高压 |

> 建议：**Go 实现 `chatbench`**，protobuf 用 `protoc --go_out` 生成，或用现成 `tests/proto_codec.py` 的思路手写最小编解码器（压测只需顶层标量字段，不需要嵌套解析，可极大简化）。

### 4.2 整体架构

```
                     ┌─────────────────────────────────────────────┐
 配置(场景/账号/目标) │              chatbench 压测器                 │
 ───────────────────►│                                             │
                     │  ┌──────────┐  ┌──────────┐  ┌───────────┐  │
                     │  │ 连接管理  │  │ 场景引擎  │  │ 指标采集   │  │
                     │  │ 连接池    │  │ 多步脚本  │  │ 延迟/吞吐/ │  │
                     │  │ 限速/并发 │  │ 状态机    │  │ 错误率     │  │
                     │  └────┬─────┘  └────┬─────┘  └─────┬─────┘  │
                     │       │  WebSocket 客户端          │        │
                     └───────┼────────────────────────────┼────────┘
                             │  ws://host:8080/ws (binary 帧 + protobuf)
                             ▼
                     ┌──────────────────────────────┐
                     │        被测聊天服务器          │
                     └──────────────────────────────┘
                             ▲
                     ┌───────┴────────┐
                     │  服务端监控采集  │  pidstat / /proc / mysqld 状态
                     └────────────────┘  （独立脚本，边跑边抓）
```

- **单机生成器**：一个进程内用 goroutine 模拟 N 个虚拟用户（每个用户一条 WS 连接）。
- **场景脚本**：把「注册/登录/加好友/私聊/群聊/离线/顶号/心跳」抽象成可编排步骤，支持按比例混合。
- **成对投递验证**：压测器内部维护「发送者→接收者」配对关系，私聊/群聊延迟 = 接收方实际收到消息时间 − 发送方发出时间。
- **可选扩展**：单机打不满时，拆成 `controller + N agent`（controller 下发场景、汇总指标），但**阶段一先不做**。

### 4.3 模块划分

| 模块 | 职责 |
|---|---|
| `conn` | WS 握手、binary 帧读写、掩码、ping/pong、close 处理、断线重连 |
| `codec` | Envelope 顶层字段编解码（type/content/target_UID/message/... 等） |
| `scenario` | 多步状态机：register → login → add_friend → ... → logout；支持 think_time、比例、随机参数 |
| `worker` | 一个虚拟用户的生命周期（一条连接 + 一个场景实例） |
| `ramp` | 阶梯/峰值/soak 的并发与速率控制（每秒建连数、每秒发消息数） |
| `metrics` | 延迟直方图（P50/P95/P99）、吞吐、错误分类统计 |
| `report` | 实时摘要 + JSONL 明细 + 结束汇总（可再导入脚本画图） |

### 4.4 输入输出

```bash
# 输入：场景 + 预置账号
chatbench run --config scenario.yaml --accounts accounts.jsonl \
              --target ws://127.0.0.1:8080/ws \
              --duration 5m --ramp-up 60s --concurrency 2000 \
              --out ./results/$(date +%s)/

# 输出
results/<ts>/
├── summary.json          # 各指标 P50/P95/P99/成功率/吞吐
├── events.jsonl          # 每条关键事件的明细（含时间戳、延迟、错误类型）
├── server_metrics.csv    # 服务端 CPU/RSS/fd/连接数 时间序列（由监控脚本写）
└── report.md             # 自动生成的可读报告
```

## 5. 压测方式（方法学）

### 5.1 负载模型

| 模型 | 做法 | 用途 |
|---|---|---|
| **阶梯加压（step）** | 并发从 100 → 500 → 1000 → 2000 → 5000，每档稳 2~5 分钟 | 找容量拐点：吞吐不再上升、P99 急剧恶化、错误率上升的位置 |
| **峰值（spike）** | 从基线瞬间翻 3~5 倍，持续 30s~60s 后回落 | 验证突发流量下的表现与恢复 |
| **长稳（soak）** | 取容量上限 60%~70% 的负载，持续 4~12h | 验证内存/内存池/fd/连接数是否随时间增长 |
| **churn（连接抖动）** | 持续「连接→登录→登出→断开」循环 | 专测对象/内存池的创建与回收 |

### 5.2 数据准备

压测账号**预先批量注册**，避免把「注册」当成压测混进结果（注册要单测）：

- 批量注册脚本生成 `accounts.jsonl`：
  `{"uid":10001,"name":"bench0001","password":"...","email":"bench0001@example.com","token":"..."}`
- 预先建立好友关系、群（如 50 人群、100 人群），生成 `groups.jsonl`。
- **使用独立测试库**，压测结束后可清空，避免污染数据；建议 `db_conn_count` 单独调大对比。

### 5.3 指标定义（客户端侧）

| 指标 | 定义 | 统计 |
|---|---|---|
| 握手延迟 | 发起 TCP 连接到收到 101 响应 | P50/P95/P99 |
| 登录延迟 | 发 `login` 到收到 `login_success` | P50/P95/P99 |
| 私聊端到端延迟 | A 发 `private_chat` → B 实际收到 `private_chat` | P50/P95/P99 |
| 群聊广播延迟 | A 发 `group_chat` → 第 i 个群成员收到 | P50/P95/P99（按群规模分档） |
| 离线补发延迟 | 目标登录后，从登录成功到收到离线消息 | P50/P95/P99 |
| 吞吐 | 每秒发送消息数 / 每秒投递成功数 | 时间序列 |
| 错误率 | 握手失败、超时、断开、坏帧、业务失败 的占比 | 按类型分类 |
| 丢消息率 | 已发送但超时未投递的消息占比（应为 0） | 0 容忍 |

### 5.4 服务端侧指标

用独立脚本边跑边抓（写进 `server_metrics.csv`）：

- CPU 使用率（`pidstat` 或 `/proc/<pid>/stat`）
- 内存 RSS（`/proc/<pid>/status` VmRSS）
- 打开 fd 数（`ls /proc/<pid>/fd | wc -l`）
- 连接数：`ss -tn state established '( sport = :8080 )' | wc -l`
- MySQL：连接数、慢查询（`SHOW PROCESSLIST` / `SHOW STATUS`）
- 线程数：`ls /proc/<pid>/task | wc -l`

## 6. 压测内容（用例清单）

> 每项都给出「操作步骤 / 关键指标 / 初始参考阈值（需按环境校准）」。

### 6.1 连接与握手

| # | 用例 | 步骤 | 指标 | 参考阈值 |
|---|---|---|---|---|
| C1 | 握手容量 | 阶梯提升每秒建连数，保持在线 | 最大并发连接数、握手 P99、错误率 | 达到预期峰值（如 5000），失败率 <0.1% |
| C2 | 建连速率 | 短连接：连上→发一条心跳→断开，循环 | 每秒建连/断连数 | 找到服务端建连上限 |
| C3 | 空闲长连 | N 条连接只握手不发消息，挂 30min | 服务端内存/fd 增量 | fd 无泄漏，RSS 稳定 |

### 6.2 登录/注册

| # | 用例 | 步骤 | 指标 | 参考阈值 |
|---|---|---|---|---|
| L1 | 登录吞吐 | 预置账号批量 `login` | 登录 P95、每秒成功登录数 | P95 < 500ms（含 DB） |
| L2 | 注册 | 并发 `register`（唯一邮箱） | 注册成功率、邮箱唯一性并发正确 | 成功率 100%，无脏数据 |
| L3 | 顶号 | 同 UID 二次登录，旧连接应收到 `kicked offline` 并关闭 | 顶号通知延迟、旧连接清理正确 | 100% 收到，无残留在线映射 |

### 6.3 私聊

| # | 用例 | 步骤 | 指标 | 参考阈值 |
|---|---|---|---|---|
| P1 | 私聊吞吐 | N 对用户互发短消息 | msg/s、端到端 P95 | P95 < 200ms（本地回环） |
| P2 | 私聊延迟 vs 并发 | 固定发送速率，阶梯提高在线对数 | 延迟拐点 | 找到 P99 恶化的并发档位 |
| P3 | 私聊回执 | 发送方收到 `Message sent. Message ID: X` | 回执延迟、message_id 单调 | 100% 回执 |

### 6.4 群聊广播

| # | 用例 | 步骤 | 指标 | 参考阈值 |
|---|---|---|---|---|
| G1 | 群广播延迟 | 1 人发群聊，K 人接收（K=10/50/100） | 第 i 个成员投递延迟、丢消息率 | 丢消息 0，P95 随群规模给出分档值 |
| G2 | 群广播吞吐 | 多群并发广播 | 全服 msg/s、广播放大倍数 | 找到 DB `store_message` 瓶颈 |

### 6.5 离线消息

| # | 用例 | 步骤 | 指标 | 参考阈值 |
|---|---|---|---|---|
| O1 | 离线落库+补发 | B 离线，A 发 N 条 → B 登录 | 补发延迟、补发条数完整性、顺序 | 100% 完整、按 id 有序 |
| O2 | 大批量离线 | 单个用户积压 1000 条再登录 | 补发耗时、是否打满发送队列 | 不触发 `max_pending_bytes` 断连 |

### 6.6 心跳与超时

| # | 用例 | 步骤 | 指标 | 参考阈值 |
|---|---|---|---|---|
| H1 | 心跳正确性 | 每条连接周期发 `heartbeat` | 收到 `heartbeat_ack` 成功率、延迟 | 100% |
| H2 | 空闲超时 | `use_heartbeat=true`，不活跃连接等待 | 超过 `heartbeat_interval` 被关闭 | 阈值 ±容差内关闭 |

### 6.7 异常与边界

| # | 用例 | 步骤 | 指标 | 参考阈值 |
|---|---|---|---|---|
| E1 | 超大帧 | 发送 > `max_message_bytes`(1 MiB) | 服务端拒绝/断开，不崩溃 | 无 crash，其余连接不受影响 |
| E2 | 坏帧 | payload_len 与实际不符 | 服务端回 `Invalid binary frame` | 不崩溃，连接可继续用 |
| E3 | text 帧 | 发 text 帧 | 服务端提示仅支持 binary | 提示正确 |
| E4 | 慢消费者 | 客户端只收不发，制造发送队列堆积 | 超过 `max_pending_bytes` 主动断开 | 触发 teardown，不内存暴涨 |
| E5 | 消息风暴 | 单连接极高速发消息 | 读背压生效、不丢不崩 | 有界延迟，无 OOM |

### 6.8 稳定性 / 内存池专项（本次重点）

| # | 用例 | 步骤 | 指标 | 参考阈值 |
|---|---|---|---|---|
| S1 | 长稳 soak | 70% 峰值负载跑 12h | RSS/fd/连接数曲线 | RSS 增长 <10%，无 crash |
| S2 | 连接 churn | 连续 10 万次「连接→登录→登出→断开」 | 内存池复用、RSS 回落 | 结束后 RSS 回到基线，对象无泄漏 |
| S3 | 池上限观察 | 并发 > 8192 会话 | 超过池上限后行为（回退全局 new） | 功能正常，性能可接受，无错误 |

## 7. 判定标准

- **功能正确性（硬性）**：任何用例都不得出现崩溃、数据错乱、丢消息（除明确设计为丢弃的场景）。
- **性能（参考初始值，需按实际环境标定）**：
  - 握手失败率 < 0.1%
  - 登录 P95 < 500ms
  - 私聊端到端 P95 < 200ms（同机回环）
  - 群聊广播丢消息率 = 0
  - 长稳 12h 无泄漏、无 crash
- **每次压测产出一份 `report.md` + `summary.json` 存档**，形成回归基线，后续改动（内存池、线程池、DB 池调参）跑同一场景对比。

## 8. 实施计划（分阶段）

| 阶段 | 内容 | 预计 |
|---|---|---|
| P0 | 写最小可用压测器：握手/登录/私聊 + 延迟统计（Go + 最小 protobuf codec） | 1~2 天 |
| P1 | 场景化：加好友/群聊/离线/心跳/顶号；接入阶梯加压与 summary/report | 2~3 天 |
| P2 | 服务端监控采集脚本 + churn/soak/异常用例 | 1~2 天 |
| P3 | 全量跑通，出第一份基线报告，固化为一键脚本 `./scripts/bench.sh` | 1 天 |

> 先做 **P0 的最小闭环**（能测出私聊延迟与吞吐），再逐步补齐场景，避免一开始就设计过度。

## 9. 风险与注意点

1. **本机 fd / 端口限制**：压测端 `ulimit -n`、`net.ipv4.ip_local_port_range`、`net.core.somaxconn`、`tcp_tw_reuse` 必须调大，否则客户端先被打爆，误判服务器差。服务端也要调 `ulimit -n`。
2. **压测机与被测机分离**：压测器本身吃 CPU/网络，同机跑会互相干扰；至少用 cgroup/`taskset` 隔离，理想是两台机器或两个容器。
3. **DB 是隐藏瓶颈**：聊天每条都落库，先单独确认 MySQL 能扛住；`db_conn_count=4` 很可能先满，压测时记录「业务线程池等待 DB」现象。
4. **业务线程池只有 8 线程**（`ws_server.cpp` 硬编码）：吞吐上不去先看这 8 个线程是否打满；建议压测时把 `io_threads`、`db_conn_count`、业务线程数做成可配置后再对比。
5. **数据污染**：压测账号/消息量巨大，务必用独立测试库并在结束清理；不要在线上库跑。
6. **时钟**：端到端延迟跨「发送方机器/进程」与「接收方」，单机内可对比时间戳，跨机需先做时钟对齐或用回环时间戳抵消。
7. **WS 帧细节**：客户端发送必须带掩码（RFC6455），binary 帧 opcode=0x2；长度头用网络序；处理服务端 ping 回 pong。
8. **内存池语义**：`ClassMemoryPool` 达到 8192 上限后是「回退全局 new」而非失败，所以 S3 用例不会崩，但池化收益消失——这正好是要观测的行为，别误判成 bug。
