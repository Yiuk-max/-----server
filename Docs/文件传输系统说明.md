# 文件传输系统详细说明

> 本文档按当前代码实现，详细说明文件系统如何运作、每个文件/函数/结构体的职责。
> 相关设计文档：`docs/文件系统方案.md`；数据库脚本：`sql/file_system.sql`、
> `sql/alter_existing_tables.sql`、`sql/alter_community_avatar_banner.sql`、
> `sql/alter_file_transfer_upload_meta.sql`。

---

## 1. 总体架构

文件系统与消息、网络层解耦，分四层：

```
client_session / File_handler（业务入口，解析 Envelope）
        │
        ▼
FileService（业务编排：上传/下载/暂停/续传/取消/进度/列表/删除）
   │                │
   ▼                ▼
FileStorage      I_file_repo（file_repo，MySQL）
（磁盘流式读写）   （file / file_transfer 表）
        │
        └── 通过 SendFn 回调发 Envelope + file_data，经 IClientTransport 出去
```

- **FileService**：每个 `client_session` 一个实例；不依赖具体网络层，只通过
  `send(Envelope, file_data)` 回传结果。
- **FileStorage**：只管磁盘路径和流式读写，不碰 SQL。
- **I_file_repo / file_repo**：只管 MySQL 元数据与传输会话，不碰磁盘文件本体。
- **FileTransferWatchdog**：全局后台线程，清理超时会话、tmp 临时文件和孤儿文件。

## 2. 磁盘存储布局

```
<root>/
├── files/
│   └── <type>/<storage_key前2字符>/<storage_key>
└── tmp/
    └── <storage_key>.part          # 上传中的临时文件
```

- `root` 由 `configure.json` 的 `file_storage.root` 配置，默认 `/home/ubuntu/chat_server_files`。
- `type` ∈ `avatar / emoji / image / attachment / file`。
- `storage_key` 是服务器生成的随机 hex，**不使用原始文件名**（防路径穿越/重名覆盖）。
- 上传先写 `tmp/<storage_key>.part`，完成后 `rename()` 到 `files/<type>/<aa>/<storage_key>`。
- 原始文件名只存 `file.original_name`，下载时通过 `FileMeta` 返回给客户端。

| 字段 | 含义 |
|------|------|
| id | 传输会话 ID |

## 4. 协议消息类型

| `file_transfer_pause` | C→S | 暂停 | `transfer_id` |
| `file_transfer_paused` | S→C | 已暂停 | `transfer_info` |
| `file_transfer_resume` | C→S | 继续 | `transfer_id` |
| `file_transfer_progress` | S→C | 进度响应 | `transfer_info` |

| `file_transfer_status` | C→S | 查进度 | `transfer_id` |
| `file_list_request` | C→S | 文件列表 | 分页游标 |

### 类 `FileStorage::Writer`（上传写入）

| 函数 | 作用 |

### 类 `FileStorage::Reader`（下载读取）

| 函数 | 作用 |
|------|------|
| `open()` | 以二进制只读打开文件 |
| `seek(offset)` | 定位到指定偏移（按分片下载时跳转） |
| `read(buf, max)` | 读取最多 max 字节，返回实际字节数，0 表示 EOF |

## 5.2 `src/file/sha256.h/.cpp` —— 内置 SHA-256

| 函数 | 作用 |
|------|------|
| `Sha256()` | 构造并初始化哈希状态 |
| `reset()` | 重置哈希状态 |
| `update(data, len)` | 增量喂入一段数据（可多次调用） |
| `final_hex()` | 输出 64 位小写十六进制哈希；完成后不可再 update |

## 5.3 `src/file/file_service.h/.cpp` —— 业务编排

### 类 `FileService`

构造函数：
```cpp
FileService(std::shared_ptr<RepositoryHub> repo);
```
- 从 `ServerConfig` 读取 `root / chunk_size / max_file_size / max_avatar_size / max_storage_size`。
- 持有 `FileStorage storage_` 与 `repo_->files()` 仓储。

回调类型：
```cpp
using SendFn = std::function<void(const chat_proto::Envelope&, const std::string&)>;
```
- 第一个参数是 protobuf 信封，第二个参数是**原始文件二进制**（可为空）。
- 由 `File_handler` 注入 `session.send_file_packet`。

### 上传

| 函数 | 作用 |
|------|------|
| `upload_init(uid, msg, send)` | 校验大小、生成 storage_key、创建 tmp 文件、写 `file_transfer(uploading)`，回 `file_upload_ready` |
| `upload_chunk(uid, msg, file_data, send)` | 按 `meta.chunk_index/offset` 将分片写到 tmp 对应偏移，更新接收位图与进度，落库 |
| `upload_done(uid, msg, send)` | 校验所有分片到齐 → `commit()` 原子改名 → 磁盘重算 SHA256 → 写 `file` 行 → 回填 `file_transfer.file_id` → 回 `file_upload_complete` → 触发存储淘汰 |
| `upload_resume(uid, msg, send)` | 按 `transfer_id` 从 DB 恢复上传上下文，重建 writer，回 `file_upload_ready` |

### 下载

| 函数 | 作用 |
|------|------|
| `download_init(uid, msg, send)` | 按 `file_id` 查文件，创建 `file_transfer(downloading)`，回 `file_download_ready`（不自动推块） |
| `download_chunk(uid, msg, send)` | 按 `transfer_id + chunk_index` 读取该分片并回 `file_chunk`；更新进度；最后一块置 completed |

> 下载是**拉取式**：客户端逐块发 `file_download_chunk`，天然背压、可中断。

### 控制

| 函数 | 作用 |
|------|------|
| `pause(uid, msg, send)` | 会话置 `paused`，回 `file_transfer_paused` |
| `resume(uid, msg, send)` | 会话按方向回到 `uploading/downloading`，回 `file_transfer_progress` |
| `cancel(uid, msg, send)` | 置 `cancelled`，若内存有 writer 则删除 tmp |
| `status(uid, msg, send)` | 查询会话，回 `file_transfer_progress` |

### 管理

| 函数 | 作用 |
|------|------|
| `list(uid, msg, send)` | 分页查当前用户上传的文件，回 `file_list_response` |
| `remove_file(uid, msg, send)` | 删除磁盘文件 + `file` 行，回 system 提示 |
| `evict_if_needed()` | 存储总量超过 `max_storage_size` 时，删除最老文件直到低于上限 |

### 内部工具

| 函数 | 作用 |
|------|------|
| `send_system(text, send)` | 发一条 system 消息 |
| `fill_file_proto(f, out)` | 把 `file_meta_info` 填进 `chat_proto::FileMeta` |
| `fill_transfer_proto(t, out)` | 把 `file_transfer_info` 填进 `chat_proto::FileTransferInfo` |

### 结构 `UploadCtx`（上传上下文）

| 字段 | 作用 |
|------|------|
| transfer_id / storage_key / type / original_name / mime_type / tmp_path | 上传会话元数据 |
| total_size / chunk_size / chunk_count | 大小与分片信息 |
| transferred / next_chunk_index | 进度与断点 |
| declared_hash | 客户端声明的 sha256 |
| resumed | 是否断线重续 |
| received | 分片接收位图（1 bit/chunk） |
| writer | 磁盘写入器 |

## 5.5 `src/file/file_watchdog.h/.cpp` —— 后台清理

| 函数 | 作用 |
|------|------|
| `get_instance()` | 单例 |
| `start()` | 启动后台线程（幂等） |
| `stop()` | 停止线程 |
| `loop()` | 每 60s 执行一次清理 |

`loop()` 做两件事：
1. **清理超时会话**：查 `get_stale_transfers(timeout)`，删除 `tmp/<...>.part`，会话置 `failed`。
2. **孤儿回收**：每 10 轮（约 10 分钟）枚举 `files/` 下文件，`file_exists()` 为 false 的删除。

## 6. 完整流程

### 6.1 分片上传（顺序/乱序均可）

```
客户端                          服务端
  file_upload_init ───────────► 校验大小 → 建 tmp writer + file_transfer(uploading)
  file_upload_ready ◄────────── transfer_id, chunk_size, chunk_count
  file_chunk × N ─────────────► 按 offset write_at → 置位图 → update_transfer
  file_upload_done ───────────► 位图全齐？commit 到正式路径
                                 重算 sha256 → 与 declared_hash 比对
                                 写 file 行 → 回填 file_transfer.file_id
  file_upload_complete ◄─────── file_id + transfer_info
```

### 6.2 分片下载（拉取式）

```
客户端                          服务端
  file_download_init ─────────► 建 file_transfer(downloading)
  file_download_ready ◄─────── file_meta + transfer_info
  file_download_chunk(0) ────► seek(0) → read → file_chunk(0)
  file_download_chunk(1) ────► seek(chunk) → file_chunk(1)
  ... 逐块拉取（背压）...
  最后一块完成后 ─────────────► transfer = completed
```

### 6.3 暂停 / 继续

- 客户端发 `file_transfer_pause` → 服务端置 `paused`。
- 下载暂停 = 客户端不再发 `file_download_chunk`；继续 = 从 `next_chunk_index` 继续拉。
- 上传暂停 = 客户端不再发 `file_chunk`；继续 = 从断点继续发。

### 6.4 断线重连续传（上传）

```
上传中发了几块 → 断线（服务端 writer 随 session 析构，tmp 文件保留）
重连登录 → file_upload_resume(transfer_id)
服务端：get_transfer → 恢复 storage_key/type/... 与 received 位图
        → open_append(tmp) 重建 writer → 回 file_upload_ready
客户端：从 next_chunk_index 继续发块 → file_upload_done → 完成
```

### 6.5 乱序重组

- `upload_chunk` 使用 `meta.offset` 定位写入，不要求按序到达。
- `received` 位图记录已收到的块。
- `upload_done` 要求 `all_received()` 才允许完成。
- 最终 sha256 从磁盘完整重算，保证乱序上传内容正确。

### 6.6 存储超限淘汰

- 上传完成写 `file` 后调用 `evict_if_needed()`。
- 若 `SUM(size) > max_storage_size`，按 `created_at ASC` 删除最老文件（磁盘 + DB），直到低于上限。

## 7. 关键设计点

1. **传输与存储分离**：`FileService` 不碰网络，`FileStorage` 不碰 SQL，`file_repo` 不碰磁盘。
2. **大文件不整块进内存**：写入用 `write_at` 流式，下载用 `seek + read` 单块读取。
3. **路径安全**：磁盘路径只由服务器生成的 `storage_key` 计算。
4. **背压**：下载采用客户端拉取式，一次只处理一个分片。
5. **可恢复性**：断点信息（位图、next_chunk_index、上传元数据）全部落 `file_transfer`。
6. **完整性**：上传完成后磁盘重算 sha256，写入 `file.hash` 并与客户端声明值比对。
