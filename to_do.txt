2026-05-29 更新（发送/序列化相关修正）
- 在 `Text_msg_handler::package_message` 中：
    - 使用 `nlohmann::json` 将要发送的消息序列化为 JSON，添加 `type` 字段（如 `system`/`group`/`spk`）。
    - 将 JSON 字符串长度使用 `htonl` 转为网络字节序写入 4 字节包头，并将包头与消息体拼接成完整包。
    - 不再把 handler 内部的整个 `out_buffer` 传给 sender；改为直接将本次构造的已序列化包交给 `sender->add_to_out_buffer()` 统一处理。

- 在 `Text_recver_sender`：
    - `Text_msg_sender::add_to_out_buffer` 优化为仅在发送缓冲区由空变非空时调用 `epoll_ctl(..., EPOLL_CTL_MOD, ..., EPOLLIN|EPOLLOUT|EPOLLET)`，避免频繁系统调用。
    - `Text_msg_sender::send_msg` 使用 `send()` 循环发送缓冲区数据，正确处理部分发送与 `EAGAIN/EWOULDBLOCK`，发送完毕时取消写事件注册（仅保留读事件）。
    - `Text_msg_recver::process_recv_data` 在解析包头时使用 `ntohl` 将网络字节序转换为主机字节序后再取出消息体长度，完成粘包处理逻辑。

- 影响与注意项：
    - 已移除 handler 与 sender 之间的冗余双缓冲（现在 `sender` 统一管理发送缓冲区）。
    - 建议后续对 `process_recv_data` 增加消息长度上限检查、`epoll_ctl` 返回值检查与 SIGPIPE 处理，以提升健壮性。

这些改动位于：
- `Text_msg_handler.cpp`（package_message 序列化与 htonl）
- `Text_recver_sender.h` / `Text_recver_sender.cpp`（add_to_out_buffer 优化、send_msg、process_recv_data 使用 ntohl）

2026-08-03 修复(主从 reactor 下登录无效问题)
- 问题根因：登录时 client_session::login 会把 session_manager 中该连接的 key 由 fd 换成 UID
  （私聊/群聊转发需按 UID 查找）。但 sub_reactor 事件循环原先一直用 find_session(fd) 按 fd 找 session，
  登录后 key 变了导致 find_session(fd) 返回 nullptr，EPOLLOUT 写事件无人处理，登录成功响应发不出去，
  表现为"登录无响应、实际未登录"。
- 解决方案（方案A）：sub_reactor 增加独立于 session_manager 的 fd->client_session 映射 sessions_by_fd，
  事件循环改用它查找连接，不再依赖会被更换的 key。
    - epoller.h   : 新增成员 sessions_by_fd 及 get_session/set_session/erase_session 接口
    - epoller.cpp : add_connect/loop/pool_add_task/remove_client 改用 fd 映射；新增三个接口实现；
                    并补充 #include "client_session.h"
- 分工：
    - session_manager 保留按 UID 查找，用于 private_chat / group_spk 的消息转发
    - sub_reactor 的 fd 映射仅负责 epoll 事件循环，二者共享同一 client_session 对象(shared_ptr)
- 作用：登录成功后 EPOLLOUT 写事件可被正确处理，登录成功响应正常返回，用户可正常登录。

2026-xx-xx 修复：注册无响应（accounts_mutex 重入死锁）
- 根因：account_manager::register_account 持有 accounts_mutex 的锁时，调用 add_social_module
        -> new social_module(UID) -> 构造函数里 find_account(UID) 再次对同一把
        accounts_mutex 加锁。std::mutex 不可重入，同一线程二次加锁造成永久死锁，
        于是注册永远处理不完、不返回任何响应。
- 修复：把 add_social_module 移出 accounts_mutex 的锁作用域（先写入账户并保存 UID，
        释放锁后再创建社交模块）。

2026-xx-xx 重构：方案 3b（重拆）——connection 彻底独立，epoll 事件循环直接面向 connection
- 目标：在 3a 基础上再进一步——彻底拆出 connection，client_session 退化为纯"会话+业务"，
        且 sub_reactor 的事件循环不再面向 client_session，而是直接面向 connection。
- 新增/改造：
    - connection.h/.cpp
        - 新增 process_incoming()：循环切出所有完整帧，逐帧回调 session->on_message()
          （供线程池任务调用；持 recv_mtx_ 保护接收缓冲，避免与 IO 线程 append 竞争）
        - 新增 attach_session(shared_ptr<client_session>)：绑定业务会话
        - next_frame() 改为私有；append_raw_data 加锁
        - recv_mtx_ 成员：串行化「append 追加」与「process 切帧」
        - 持有 shared_ptr<client_session> session_
    - client_session.h/.cpp
        - 不再构造/持有 connection（把 make_unique<connection> 移除）
        - conn_ 类型 unique_ptr -> weak_ptr<connection>（弱引用回指，防悬垂+防环）
        - 新增 set_connection(const shared_ptr<connection>&)
        - handle(raw_message) -> on_message(json_part, file_part)
          （只解析 JSON + 按 type 策略分发，切帧逻辑已上移到 connection）
        - package_message / exit_self 改用 conn_.lock() 安全访问
        - 构造函数改为无参（由 sub_reactor 创建），构造时调用 init_()
    - epoller.h/.cpp
        - sessions_by_fd(fd->client_session) 改为 connections_by_fd(fd->connection)
        - get/set/erase_session -> get/set/erase_connection
        - add_connect：创建 connection + client_session，set_connection + attach_session 双向绑定
        - pool_add_task：append_raw_data(received_data) -> 提交 conn->process_incoming 到线程池
        - loop：EPOLLOUT -> conn->handle_write()；EPOLLIN -> 读数据 -> pool_add_task
        - remove_client：erase_connection + session_manager.remove_session(fd)
- 关键设计（安全/防环）：
    - 对象关系单持有链：sub_reactor -> connection -> client_session；会话用 weak_ptr 回指 connection。
    - 即使 epoll 已回收 connection 而会话仍在 session_manager（连接断开未登出），
      package_message 经 conn_.lock() 失败即安全跳过，不再有悬垂访问。
- 注意：
    - connection.cpp 需 #include "client_session.h"（回调 on_message）
    - client_session::conn() 仅在"本连接消息处理期间"调用（此时线程池任务持有 connection，
      weak 锁必成功）；跨连接转发一律走 package_message（内部 lock，安全）。
- 遗留问题（3b 前已存在，本次未改）：连接异常断开但已登录用户不会主动从 session_manager
  移除（remove_client 只按 fd remove，登录后 key 变 UID），导致断线后 is_online 仍为 true、
  会话残留；由于会话用弱引用回指 connection，至少不会再产生悬垂崩溃。
